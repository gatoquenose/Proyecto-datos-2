## 3. Requisitos oficiales (resumen del enunciado)
1. Aplicación web (ReactJS + TypeScript): al ingresar, formulario de registro o autenticación. Autenticado, lista de videos (propios + públicos de otros) ordenable por título, autor (usuario que sube) y fecha de carga; el ordenamiento se hace en el API de metadata; paginación (no traer la lista completa). Puede escoger un video para reproducirlo o gestionar su metadata. Reproducción con reproductor open source (Shaka o Dash.js), por lo que el streaming debe ser compatible. Subir y eliminar videos, modificar metadata, gestionar acceso público/privado. Cada usuario tiene una cuota de almacenamiento que NO se puede modificar; al alcanzarla no se permiten nuevas subidas.
2. API de streaming (C++): recibe peticiones del reproductor y devuelve los bloques del video; también transcodifica al subir, con FFmpeg.
3. API de metadata (C++): autor, duración, fecha de carga, tema, título, etiquetas, etc.; datos en MongoDB; resuelve orden y paginación.
4. API de usuarios (C++, REST): registrar, actualizar, eliminar y consultar; usuarios en archivo binario con índice de árbol B en disco.
5. Dashboard: todos los componentes con OpenTelemetry (traces y métricas) consumidos por Aspire, Prometheus o similar; métricas a criterio, suficientes para entender el rendimiento.
   Orientación a objetos obligatoria. Repositorio GitHub con SPEC.md; V1.0 y V2.0 como tags o ramas separadas.

## 4. Reglas de ingeniería
- POO: clases de una sola responsabilidad, interfaces abstractas (IUserRepository, IVideoRepository, ITranscoder, IClock...), inyección de dependencias por constructor, composición sobre herencia; patrones solo si se justifican.
- Cero malas prácticas: RAII y smart pointers (sin new/delete crudos), sin globales ni singletons mutables, sin números/strings mágicos, sin código duplicado ni muerto, funciones cortas, const-correctness, errores manejados explícitamente, sin secretos en código. clang-format y clang-tidy (C++ Core Guidelines) sin advertencias. TypeScript strict, sin any; ESLint limpio.
- Logging estructurado JSON, validación de entradas, README por componente, pruebas desde el inicio (GoogleTest en C++, Vitest en el frontend).

## 5. Arquitectura y decisiones validadas
- Tres APIs C++ separadas + frontend + OpenTelemetry Collector + Aspire Dashboard + Prometheus + Grafana + MongoDB, todo en Docker Compose. Puertos del host: Users 8081, Metadata 8082, Streaming 8083 (mapeo 8081:8080, 8082:8080, 8083:8080).
- Base de las APIs: http://localhost:{port}/api/v1. Error común: { code, message, details (nullable), traceId }.
- Autenticación: JWT HS256 con clave compartida por variable de entorno, duración configurable, SIN endpoint de refresh (al expirar, vuelve a iniciar sesión). Token de servicio independiente para /internal/*. Contraseñas con Argon2id.
- Los APIs son los dueños de sus datos. Streaming consulta a Metadata y a Users por HTTP con el token de servicio.
- Cola de transcodificación en memoria detrás de una interfaz sustituible (en V2 podrá ser RabbitMQ/Kafka); los videos que queden en processing tras un reinicio se pueden reintentar.
- Reproducción: DASH con JWT en el header Authorization mediante un request filter de Shaka (no en la URL). CORS restringido a la URL del frontend: permitir el header Authorization, responder OPTIONS (hay preflight por segmento), exponer Content-Range y Accept-Ranges.
- Eliminación: lógica primero y física coordinada por Streaming. HTTP interno en Compose; TLS en un reverse proxy más adelante. Identificadores UUID. pageSize máximo 50.
- Observabilidad: Collector como punto intermedio; Aspire para trazas y logs, Prometheus + Grafana para métricas y dashboards provisionados.

Seguridad: bearerAuth global (JWT); serviceToken solo en /internal/*; públicos (security: []): POST /users, POST /auth/login, GET /health, GET /ready. Validar con: npx.cmd @redocly/cli lint docs/openapi/users.yaml docs/openapi/metadata.yaml docs/openapi/streaming.yaml, con redocly.yaml en la raíz (extends recommended; reglas no-server-example.com y operation-4xx-response desactivadas). Objetivo: 0 errores. Trampas de YAML: "nullable" exige "type"; entrecomillar descripciones o ejemplos con comas o dos puntos (por ejemplo Cache-Control).
Códigos de error: 400 VALIDATION_ERROR, INVALID_CURSOR; 401 MISSING_TOKEN, INVALID_TOKEN, TOKEN_EXPIRED, INVALID_CREDENTIALS (solo POST /auth/login, mensaje genérico "Usuario o contraseña incorrectos." sin revelar si el usuario existe); 403 FORBIDDEN, QUOTA_EXCEEDED; 404 NOT_FOUND; 409 CONFLICT, USERNAME_EXISTS, EMAIL_EXISTS, INVALID_STATE; 413 PAYLOAD_TOO_LARGE, QUOTA_EXCEEDED; 415 UNSUPPORTED_MEDIA_TYPE; 422 UNPROCESSABLE_ENTITY; 500 INTERNAL_ERROR; 502 DEPENDENCY_ERROR; 503 SERVICE_UNAVAILABLE.
Users API: createUser POST /users (username 3–64 con patrón ^[A-Za-z0-9_.-]+$, email, password 8–128); login POST /auth/login {username, password} -> {accessToken, tokenType, expiresIn, user}; getCurrentUser GET /users/me; getMyQuota GET /users/me/quota -> {quotaBytes, usedBytes, remainingBytes}; GET /users/{id} y GET /users?username=&email=&pageSize=&cursor= (a otros usuarios solo se muestran id y username; el email solo lo ve el propio usuario); updateUser PATCH /users/{id} (solo email; username, quotaBytes, usedBytes y passwordHash NO son editables; NO existe PATCH /users/me); deleteUser DELETE /users/{id}. Internos: POST /internal/quota/reservations, POST /internal/quota/reservations/{reservationId}/settle, POST /internal/quota/reservations/{reservationId}/release (idempotentes por reservationId). GET /health, GET /ready.
Metadata API: createVideo POST /videos (title 1–200, description 0–5000, author 0–200, topic 0–100, tags máx 30 de máx 50 caracteres, visibility public|private; se crea con status processing); getVideo GET /videos/{id}; updateVideo PATCH /videos/{id} (solo title, description, author, topic, tags, uploadedAt); updateVideoVisibility PATCH /videos/{id}/visibility; deleteVideo DELETE /videos/{id} (solo dueño; pide a Streaming borrar archivos antes de confirmar; libera cuota); listVideos GET /videos?sortBy=title|author|uploadedAt&order=asc|desc&cursor=&pageSize=1..50&q=&owner=me -> {items, nextCursor (nullable, opaco)}. Sin autenticación no se puede usar. durationSeconds, sizeBytes, status, ownerId y ownerUsername no son editables por el usuario. Internos: POST /internal/videos/{id}/processing-complete, /processing-failed, /streaming-deleted.
Streaming API: startUpload POST /videos/{videoId}/upload {fileName 1–255, contentType, totalBytes, chunkSize} -> 201 {uploadId, videoId, reservedBytes, receivedBytes, status: uploading}; uploadChunk PUT /uploads/{uploadId}/chunks/{chunkNumber} con Content-Range y X-Chunk-Checksum obligatorio (SHA-256 hexadecimal en minúscula de los bytes del fragmento) -> 204; getUpload GET /uploads/{uploadId}; completeUpload POST /uploads/{uploadId}/complete {fileChecksum: SHA-256 hexadecimal en minúscula del archivo completo, obligatorio}; checksum inválido -> 400 VALIDATION_ERROR con details; cancelUpload DELETE /uploads/{uploadId}; getManifest GET /videos/{videoId}/manifest.mpd (application/dash+xml); getDashSegment GET /videos/{videoId}/dash/{path} (video/mp4, audio/mp4, Range, Cache-Control inmutable); getThumbnail GET /videos/{videoId}/thumbnail; getProcessing GET /videos/{videoId}/processing; GET /health, GET /ready. UploadStatus: uploading, queued, processing, published, failed. Antes de iniciar una subida se verifica con Metadata que el video existe, pertenece al usuario del JWT, está en processing y no tiene otra subida activa.

## 7. Modelos de datos
users.dat (archivo binario propio, sin motor de BD): cabecera de 4096 bytes + registros fijos de 1024 bytes; little-endian, UTF-8 con longitud explícita. Registro: magic/version/flags 8, UUID 16, username 128, email 256, hash Argon2id 128, quotaBytes 8, usedBytes 8, createdAt 8, updatedAt 8, siguiente offset de la lista libre 8, CRC32C 4, reservado hasta 1024. Flags: ACTIVE 0x0001, DELETED 0x0002. Crece por bloques configurables (inicial 1 MiB); los borrados se enlazan en una free-list y se reutilizan antes de crecer.
users.idx (árbol B en disco): páginas de 4096 bytes. PageHeader: magic u32, version u16, pageType u16 (interna, hoja, libre), pageId u64, parentPageId u64, keyCount u16, flags u16, leftSibling u64, rightSibling u64, freeSpaceOffset u16, checksum CRC32C u32 (calculado con el campo en cero), reservado. Hojas: keyType u8 (username|email), keyLength u16, keyBytes, recordOffset u64. Internas: claves y punteros a hijas. El orden máximo se calcula del tamaño real de la página (no se fija arbitrariamente). Hojas enlazadas, índices independientes por username y email, split al llenarse, merge o redistribución al quedar bajo el mínimo, lista de páginas libres.
Consistencia y recuperación: WAL para registros e índice; temporal + fsync + rename atómico cuando corresponda; al abrir: validar cabecera, validar checksum de cada página accedida, reejecutar el WAL pendiente, validar que los offsets apunten a registros válidos; si el índice no es recuperable, rechazar el arranque normal y ofrecer rebuild-index. Concurrencia: std::shared_mutex (lectores concurrentes, un escritor) + bloqueo de archivo del SO; las reservas de cuota se serializan dentro del repositorio.
Cuota: se asigna al registrar (valor por defecto configurable, p. ej. 5 GB) e INMUTABLE: no existe operación para modificarla. Las reservas se guardan en un registro persistente (reservationId, userId, bytes, estado, createdAt, expiresAt) con expiración y limpieza de reservas abandonadas; reserve, settle y release son idempotentes; el contrato define cómo se libera la cuota al eliminar un video ya publicado.
MongoDB, colección videos: _id (UUID), ownerId, ownerUsername (desnormalizado para ordenar por autor), title, description, author, topic, tags, durationSeconds, uploadedAt, visibility, sizeBytes, status (processing|ready|failed), createdAt, updatedAt. Índices: (ownerId, campo, _id) y (visibility, campo, _id) para title, ownerUsername y uploadedAt; índice de texto SOLO sobre title, tags y topic (no comodín $**); collation insensible a mayúsculas en índices y consultas. Listado = (ownerId = usuario actual) OR (visibility = public); owner=me devuelve solo los propios. El cursor contiene el último valor ordenado y el _id (desempate determinista). Validar con explain().
Streaming y reservas: storage/uploads/{userId}/{uploadId}/chunks/ y /source; storage/dash/{videoId}/manifest.mpd y segmentos; storage/thumbnails/{videoId}.jpg. Estados: created -> uploading -> queued -> processing -> published | failed. La reserva inicial = tamaño del original + multiplicador configurable para transcodificados + miniatura; al terminar se ajusta (settle). Si FFmpeg falla: borrar artefactos parciales, liberar la reserva y marcar failed. Si el tamaño real excede lo reservado y la cuota no alcanza, el procesamiento falla de forma explícita.
Transcodificación: FFmpeg a MPEG-DASH (fMP4, segmentos de 4 s, audio AAC, representaciones 240p, 360p, 480p, 720p y 1080p solo si el original las soporta, sin escalar hacia arriba), miniatura y duración. Cola asíncrona con pool de workers limitado. Interfaz ITranscoder con FfmpegTranscoder; FFmpeg se ejecuta con argumentos separados, nunca por concatenación de texto del usuario.

## 12. Estado actual y siguiente paso
Hecho: F0 (SPEC.md y contratos validados con Redocly), F1 (base del frontend), F2 (registro, login, perfil), F3 (lista con orden, búsqueda, paginación y miniaturas autenticadas), F4 (reproducción DASH con fixture sintético, sondeo y acciones del dueño). F5 (siguiente): subida y gestión. Plan aprobado con estos ajustes: (1) el SHA-256 del archivo completo se calcula de forma incremental con sha256.create().update(...) en una sola pasada, leyendo con Blob.slice en orden; cada fragmento se hashea con su propio SHA-256 para X-Chunk-Checksum. Por eso la concurrencia es 1 en v1 (configurable solo si el hash del archivo se calcula en una pasada aparte). Un reintento de fragmento no vuelve a actualizar el hash incremental. (2) Para reanudar tras recargar, se guarda { uploadId, videoId, fileName, sizeBytes, contentType, chunkSize } en sessionStorage, el usuario vuelve a elegir el mismo archivo (se comprueban nombre, tamaño y tipo) y se reconstruye el estado del hash releyendo localmente los bytes ya enviados, sin volver a subirlos.
